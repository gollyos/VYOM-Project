## Implemented experience

### Native desktop shell

- Tauri 2 application named `VYOM`, identifier `ai.vyom.core`.
- Borderless, resizable window with a 960×640 minimum size and dark startup background.
- Native startup requests `show`, focus, and fullscreen.
- `F11` toggles fullscreen; `Escape` exits fullscreen.
- Rust setup includes a fallback that creates the main webview window if configuration did not create it.
- V0 permissions are deliberately minimal: base window permissions plus fullscreen, show, and focus.

### Living Core visual system

- Full-window graphite/black atmospheric environment; no website canvas, dashboard, sidebar, cards, pages, or card grid.
- Distinct central Intelligence Core made from emissive faceted icosahedrons, a wireframe shell, three orbital rings, halo, awareness point, light, and reactive wave rings.
- Deterministic 108-node neural network with proximity connections.
- Sixteen instanced ambient signal particles.
- Subtle pointer parallax, breathing, orbiting, rotation, pulsing, and state-color interpolation.
- Performance controls: memoized geometry data, buffer geometry, instancing, capped DPR `[1, 1.5]`, high-performance WebGL preference, and no post-processing pipeline.
- Minimal top identity/status line, central state readout, mock response copy, and bottom command dock.

### Real voice runtime

- A provider-neutral `VoiceProvider` contract separates UI/microphone orchestration from Gemini Live transport.
- The Rust/Tauri bridge reads `GEMINI_API_KEY` (or `GOOGLE_API_KEY`) only at runtime and establishes the authenticated WebSocket outside frontend source code.
- The default provider/model is Gemini Live with `gemini-3.1-flash-live-preview`; model and voice can be overridden through process environment variables.
- The microphone pipeline requests mono audio with echo cancellation, noise suppression, and automatic gain control, then resamples to little-endian 16 kHz PCM16 in a dedicated AudioWorklet.
- Audio is streamed in 40 ms frames. Returned base64 PCM is queued at the provider-declared sample rate (normally 24 kHz).
- Input transcription resolves the existing four Composer commands rather than creating a chat or a new page.
- Local microphone activity and Gemini's server interruption event both clear queued playback immediately and return VYOM to Listening.
- Provider disconnects attempt three bounded reconnects. Permission denial, missing microphone, missing key, API failure, disconnect, and reconnecting states are surfaced near the Core while text remains usable.
- No wake word is implemented; the microphone button explicitly starts and stops a voice session.

### Dynamic UI Composer

- Runtime input is a versioned `UIComposition` object containing metadata, visual objects, frames, and a reveal sequence.
- The schema supports status summary, agent status, approval/action, metric, line chart, pipeline/funnel, timeline, verified result, and causal/workflow diagram objects.
- All object variants are rendered through one reusable `UIComposer`; commands select structured data rather than navigate to pages.
- Composition frames use percentage-based coordinates so work surfaces form contextual constellations around the persistent center Core.
- Every composition owns its reveal order, timing, associated Core state, and object IDs. This allows a future AI brain to generate the same JSON contract.
- Surfaces use restrained partial frames, fine typography, evidence markers, SVG charts, progress lines, and semantic tones rather than a permanent card grid.
- Existing visual objects collapse before another composition is summoned, enabling in-place status → agency → developer recomposition.
- Heavy per-surface backdrop filters were removed after visual review to reduce GPU composition cost over the WebGL biome.

### Phase 4 Brain

- The Brain lives under `services/brain` and exposes local task, approval, model, health, and WebSocket event APIs.
- Tasks follow queued → understanding → planning → executing → verifying → completed/failed, with persisted pause, cancel, and approval states.
- Model IDs live in `config/models.yaml`. External entries require explicit environment model IDs and provider credentials.
- `local-rules-v1` is a limited deterministic provider for known demos and tests; it is never represented as a general cloud model.
- Routing filters unavailable/incapable providers and scores cost, speed, quality, priority, privacy, recent health, and historical task-domain performance.
- Fallbacks are bounded and observable. Failed verification cannot become a completed task.
- L2/L3 work pauses before execution. Approving a task whose tool does not exist produces a truthful failure rather than a fake external action.
- The desktop listens to operational events, maps them to Core states, shows concise activity, and renders Brain-produced `UIComposition` data through the existing Composer.
- A contextual `model-routing` primitive shows model, provider, concise reason, fallback, runtime, and cost only when relevant.

- **Resolved 2026-08-17 (Phase 17.1), was open earlier the same day:** `app/browser/browser_session.py`'s Playwright integration could block the asyncio event loop indefinitely. Root cause, found with a minimal isolated reproduction (no guessing): a Playwright browser/page created while awaited from one asyncio event loop cannot be safely awaited or torn down from a different loop - the underlying Node-driver subprocess transport belongs to the loop that created it. Every one of these test/demo scripts calls `state.X(...)` methods directly from their own outer `asyncio.run()` loop rather than through a real HTTP request, so the browser ended up bound to that loop while `main.py`'s app-shutdown code (running on `TestClient`'s separate portal loop) tried to close it - a genuine, reachable production risk, not just a test-harness artifact, since any code path that lazily touches the browser from a different task context has the same exposure. Fix: `BrowserSession` now owns ONE dedicated background thread with its own persistent event loop; every real call (`BrowserActions.perform`, `BrowserVerifier.verify`) is submitted to it via `asyncio.run_coroutine_threadsafe` and awaited by the caller through a bounded `asyncio.wait_for` (`BrowserTimeoutError` on timeout) - a stuck/slow browser call can only ever stall that one worker thread, never the Brain's own event loop, cancellation task, or watchdog. Orphan-process cleanup uses `psutil`: tracked child PIDs (with a brief settle-poll, since Chrome's own process spawns a moment after `new_page()` returns) plus a safety-net sweep of any current child process whose executable lives under the Playwright install directory (scoped by path, never by name alone, so it can never touch an unrelated Brain subprocess like a terminal-tool run or a future MCP server).
